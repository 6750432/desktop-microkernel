对《Cyber-Microkernel Runtime Architecture v1.3》的评审意见
2026-09-29  Coopanion Native Host整理

（评审依据：① 文档全文 518 行；② 2026-09-28 本项目在 Linux 上真的写了一个「原生宿主」并逐项量过
  —— 它正好是这套架构 L2+L4 的一个可运行实例。凡是带数字的结论都是当场实测的，不是估的。

零、一句话结论
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
分层、四段式启动、回退链、错误分类、边界表 —— **这些方向都对，而且本项目已经用真机把它们的一部分跑通了**。
要改的不是骨架，是三个口径：
  ① **"196 FPS 回归"这个验收目标站不住**（这台机器上物理不可达），要换成"帧时间预算 + CPU 占用"；
  ② **多线程/RenderList SPSC 在 Python 里收益被 GIL 削掉大半**，应该排在"每帧固定开销"后面；
  ③ **沙箱与"静默失败"这两块要补能力位和自检项** —— 文档防的是"崩"，而实际最容易发生的是
     "**指标一切正常，但人已经看不见/点不到了**"。

一、最值钱的三页（建议原样保留，甚至单独抽出来当 review checklist）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. **七、模块责任边界表**（模块 / 输入 / 输出 / 严禁做的事）
   这是全文最实用的东西：可以直接变成 code review 的检查项，也能拦住"Probe 里做决策""Factory 被高频调用"
   这类最常见的架构腐蚀。建议再补两行：
     · Metrics —— 严禁：在热路径做字符串拼接/内存分配；
     · HealthCheck —— 严禁：直接改后端状态（只能发事件）。
2. **两段式探测（PreProbe 无 Qt / PostProbe 有 Qt）**
   这个切分非常关键，因为 **QApplication 的初始化会改变"可用事实"**（屏幕、DPI、平台插件、
   能不能开窗口，都要等 Qt 起来才知道）；反过来，沙箱权限、GPU 驱动这些在 Qt 之前判更干净。
3. **回退链 + BackendError 分类 + FORCE_FAIL 注入**
   这条是真能救命的。本项目昨天就遇到过一次"没人会发现的失败"：
   WebGL2 上下文拿不到时角色**静默消失** —— rAF 还在跑、帧率照样 48 fps、内存也确实降了，
   所有指标都正常，就是屏幕上没有她。**如果有 FORCE_FAIL 注入 + 一条"渲染后端可用性"自检，
   这种故障在 CI 里就会暴露。** 建议把 FORCE_FAIL 从"测试策略"提升成"V0.2 必做项"。

（另外，「ProbeDiagnostics 与 ProbeResult 分离」这种细节很专业：避免把"探测超时"当成"没有 GPU"。
 这类"事实 vs 诊断"的分离，全文只有这一处写到了，值得推广到别的地方，见第三节。）

二、建议修改的七条（按严重度排）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【1】「196 FPS 回归」这个目标必须重新定义 —— 先说一下这个数从哪来？

  昨天实测（同一台机器：i7-6700 / X11 + xfwm4 合成器 / 144 Hz 屏）：
    · 把网格抽到几乎为 0（≈17 次绘制调用）时，整机最高 **145.6 fps**，CPU 已 114%；
    · 也就是说 **「窗口贴图 + 合成器」那一层就是 4~5 ms/帧的硬地板**，跟画什么无关；
    · 屏幕本身 144 Hz，再高也看不见。
  → **196 FPS 在这台机器上不可达**（除非关合成器走独占全屏，那是另一个赛道）。

  建议把验收指标从"绝对 fps"换成三个可比的量：
    · **帧时间预算**：p50 / p95（ms），而不是 fps —— 因为 fps 会被"帧率上限"和"地板"两头夹住，不反映优化；
    · **两档 CPU 占用**：目标帧率下（如 24 / 48 / 60 fps）各占多少核；闲置时降到多少
      （本项目实测：闲时从 24 降到 12 fps，CPU 直接少一半，肉眼无差）；
    · **冷启动到首帧**（本项目实测 1.0 s，官方 Electron/CQtWebEngine 路线 1.8 s）。
  并且一定要在文档里写清 **196 是在哪个平台、哪个后端、什么画质下量的** —— 否则这条回归会变成玄学。

【2】热路径纪律要写成"可量化的预算"，而不是形容词

  把"零分配"改成"最小化分配"是对的（文档已改）。但要真能指导实现，得给数字。本项目昨天的实测常量：
    · 一次 Python→Qt 的绘制调用（裁切+变换+贴图）：**10~22 µs**
    · 每格现场创建 Qt 对象（2 个 QPolygonF + 8 个 QPointF + 1 个路径）：**8~9 µs**
    · 一台 217×217 画布上、一帧 547 格：**36.4 ms**（一颗核跑满 → 27 fps）
    · 同样一帧，把"每块部件合并成一次绘制"：**0.23 ms**（光栅层快 150 倍）
  建议直接把这些写成 **「每帧跨界调用次数预算」**（例如 ≤ 200 次/帧）与 **「每帧新对象预算」**，
  并进 Metrics。经验：**这两个预算比"零分配"有用得多**，因为 Python 里真正的钱花在"跨界"和"对象创建"上，
  而不是"分配了几个字节"。

【3】线程模型排在"固定开销"之后，别让它先吃掉设计预算

  3.1/3.2/3.3 的线程模型本身没毛病，但在 Python 里要打折：
    · **GIL**：逻辑线程与渲染线程不能真并行 —— 除非渲染后端在 C++ 侧长时间放掉 GIL（QPainter 绘制时会放，
      但每帧的 Python 胶水不放）。本项目的实测：Python 侧"每帧 752 个顶点过变形链"只花 **0.14 ms**，
      而 Qt 调用 + 对象创建是它的 **200 倍**。也就是说：**先把每帧调用次数压下去，收益远大于上线程。**
    · 昨天本项目量到：单核 114% → 145 fps 时，线程才成为瓶颈。**在那之前，多线程只是把复杂度搬进来。**
  建议：V0.2/V0.3 明确"单线程事件循环 + 脏矩形"为默认路径；把 RenderList SPSC / 渲染线程列为
  **V0.4 的性能选项，且准入条件是"单线程 p95 帧时间 > 目标帧时间"**（用 Metrics 说话）。
  顺便：3.1 说"逻辑不在渲染线程跑"，3.3 说"Core::tick 跑在 Worker 线程**或**主事件循环" —— 这两处口径统一一下。

【4】不可达的承诺要分级：热切换"状态不断"容易，"画面不断"很难

  第四节的"无重启热切换"里，DPI/跨屏这类**增量重配**确实能做到无缝；但
  "显示服务切换（X11→Wayland）/ GPU 丢失（TDR）"这类**整链重建**，现实中表面必须重建，
  画面必然黑一下或闪一下。建议写成：
    · 核心状态机与时间轴 **不丢**（这条能保证）；
    · 画面允许 **N 帧重建窗口**（给个上限，例如 ≤ 3 帧）；
    · 并把它做成可测量：**重建耗时 p95** + **黑帧数**。
  另外 HealthCheck（10 s 心跳）触发 RuntimeCapabilityChanged 需要**防抖动风暴**：
  刚切过去又失败 → 再切 → 死循环。建议：连续 N 次失败才升级；切换后给冷却期 + 指数退避。

【5】沙箱章节要补的不是 GPU，是"窗口层能力"

  2.3 的沙箱裁剪写得很好（"不要把沙箱等同于禁用 GPU"是对的）。但从本项目踩坑的经验看，
  **沙箱里最容易翻车的不是 GPU，而是窗口/输入这几件事**：
    · 能不能直连 X（沙箱里 `XOpenDisplay` 可能直接失败）；
    · 能不能设**输入区形状**（XShape；设不了就变成"整窗吃鼠标"）；
    · 能不能全局查询光标位置（很多"看向鼠标"的实现靠它）；
    · 能不能置顶 / 不进任务栏 / 不抢焦点。
  这些一旦失败，表现是"**看起来在跑，但点不到/看不到/穿不过去**"，比 GPU 失败更难查。
  建议 ProbeResult 里显式加四个能力位：
      can_open_display / can_set_input_region / can_query_pointer / can_always_on_top
  （这四个和 gpu_api_support 一样是事实，不是策略。）

【6】补一节"**静默失败自检**"（这是文档目前最大的空白）

  文档把可观测性写得很全（ILogger/Metrics/HealthCheck），但采样的是"性能"；
  而桌宠这类程序真正致命的故障是**"指标正常但已经废了"**。建议在 6.3 里加三类检查项（都是本项目踩过的）：
    · **输入区自检**：把当前帧 alpha 的包围盒和"实际设给系统的输入区"比一下；
      不一致就说明"她在那儿，但鼠标穿过去了"或反之（本项目踩过：mask 为空 → 整窗吞鼠标）；
    · **呈现自检**：present 返回成功后，抓一帧（或一个像素块）确认画面**真的变了**；
      失败案例：rAF 照跑 48 fps，canvas 是空的（WebGL2 拿不到）；
    · **资源自检**：句柄/纹理/进程内存是否单调增长（本项目那边长跑 1 小时涨到 800 MB）。
  这三条的共同点：**它们都不会抛异常**。建议写成"健康度三问"，每 10 秒顺手做一次，成本和 HealthCheck 一样。

【7】Metrics 通道：V0.2 就写日志可以，但**格式先定成一行 JSON**

  6.4 说 V0.2 写日志、V0.4 接 Prometheus/OTel —— 同意。但建议 V0.2 的日志**就按"一行一个 JSON"写**
  （`{"t":"frame","p50_ms":17.2,"p95_ms":24.1,"fps":23.8,...}`），这样 V0.4 换通道时采集端不用重写。
  本项目昨天的教训很直接：统计是从日志里**正则抠**出来的（`统计：5s 内 120 帧（23.8 fps）｜每帧 2.1 ms…`），
  换成 JSON 能省掉一堆解析代码和踩坑。

**最值得写进文档的一条实测结论**：
  "**把每块部件从 N 次绘制调用合并成 1 次，比任何渲染算法优化都值钱**"
  —— 逐格裁切 36.4 ms vs 合并绘制 0.23 ms（同一帧、同一画质、逐像素比过：90.7% 完全相同，
     差异全在格子接缝的半像素抗锯齿）。
  这条建议放进 3.1 的"热路径三大纪律"里当第 4 条：**每帧的"跨界调用次数"是首要预算**。

顺带三条 Python 特有的坑（建议进文档，因为这套架构明显是 Python 宿主）：
  · **长生命周期的 Qt 对象必须被 Python 对象强引用**：QTimer / QWebSocketServer / QShortcut
    被 GC 掉时**不报错、静默失效**（本项目昨天一个 HUD 定时器就因为局部变量被回收，牌子永远停在「…」；
    更早一次是 QWebSocketServer 被回收，"listen 成功"但端口根本没监听）；
  · **不要用 process_time 量单函数**：它是整进程 CPU（Qt 内部线程的账会算进来），
    本项目因此把 0.5 ms 的函数量成 20 ms；单函数要用 thread_time；
  · **跨进程通信要量整棵进程树**：桌宠常常还有解码子进程（ffmpeg 之类），
    只盯主进程会把主要成本漏掉。

四、如果这份是要发给 PAIL 的
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
建议把它定位成 **"第三方宿主（窗口层）参考架构"**，而不是"上游要照搬的实现"：
  · 上游是 Node/TS + Electron，这份文档是 **宿主侧**（Python/Qt）的架构；

    这三样写清楚，别人才敢照着写第二个宿主 —— 本项目昨天就是靠这三样把宿主换掉的，一共没改核心一行。

五、细节勘误 / 小问题（逐个，好改）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. 2.3 命名混了"事实"和"建议"：`display_server_resolved` 是事实、`partial_update_hint` 是提示、
   `gpu_candidate` 是推断。建议统一后缀（`*_fact` / `*_hint` / `*_candidate`）并在注释里写明
   "hint 只给 Factory 参考，不是事实"——否则下游会拿提示当事实用。
2. 2.5 伪代码里 `create_renderer(cfg.renderer_preference, caps)` 没体现"renderer 依赖 platform 的 surface"。
   实际签名建议 `create_renderer(platform, caps, cfg)`，并在边界表里写明"Renderer 不得自己创建窗口表面"。
3. 2.5 的 `skip_related_backends` 很好，但缺"**跳过之后还要不要重试**"：GPU 丢失后如果驱动恢复了，
   需要有重新上探的机会（配合 HealthCheck）。建议写成"跳过 = 降级到本会话结束，或直到下次 ReProbe"。
4. 3.4 的关闭时序很好；建议补一句"**关闭阶段禁止再创建任何 Qt 对象**"（C++ 侧已析构时创建会崩，
   这是 Python/Qt 混合最常见的一类退出崩溃）。
5. 6.1 说"所有模块禁止直接 import logging" —— 这条在 Python 里有代价（包装一层就是每帧调用多一次跨界）。
   建议改成"**热路径禁止打日志**（无论用什么门面）"，这比"禁止 import logging"更贴近目的。
6. 七的边界表里 `ScreenDpi`："不重建后端（除非必要）" 太模糊 —— 建议给判据：
   "仅当缩放比变化 > 5% 或跨屏导致 surface 失效时才重建"。
7. 8 的分期里 V0.2 砍掉 ILifecycle 是对的（认同），但**"弱引用缓存基础版"建议也一起砍**：
   没有热切换就没有"多次 acquire/release"的需求，先做反而容易写出半吊子的引用计数。
8. 建议加一节"**为什么不是现在这套**"：把你现在的实现（Python/Qt + X11 原生穿透 + QPainter）
   和"通用微内核 + QRhi + DComp + Wayland"的差距、迁移成本、收益写清楚 ——
   架构文档如果没有"不做什么"，落地时一定会膨胀。
