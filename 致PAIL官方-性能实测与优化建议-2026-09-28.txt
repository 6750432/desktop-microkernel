关于「web/whale」这个角色的性能实测与优化建议

  本项目只改了「宠物窗口那一端」，核心（cortico / desktop-pet world）一个字节没动，

零、先说结论
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
web/whale 这个角色本身做得很讲究（骨骼、弹簧、脸部程序化绘制、配色交叉淡入），
但它有一条**每帧都在跑的固定开销**，跟平台无关，改掉一处就能省不少：

  ★ 每帧都把整张脸重画一遍、再当作纹理上传一次（figure.js:441-442 + rig.js:65-77），
    而 upload() 里每次都连带 gl.generateMipmap()。也就是**每帧一次 390×252 的整图上传
    + 一整套 mipmap 重建**。参数没变的那些帧是纯浪费；参数变了其实也只需要更新变化的那小块。

其次是渲染管线的几处「可以少干活」的地方（第三节 ★★ 那几条）。

另外有一个会让角色**静默消失**的坑（第四节），建议加个可见的降级，这个比性能更值得改。

一、本项目做了什么（为什么这份报告可信）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
你们留的扩展点 `CORTICO_DESKTOP_PET_HOST`（worlds.desktop-pet 的 window-host.ts）非常好用：
本项目没改核心，只用它把宠物窗口换成了自己写的**原生宿主**（Python + Qt，没有 Electron、
没有 Chromium/QtWebEngine），window.petHost 那套垫片也照你们的设计补上了。

因为宿主是本项目自己写的，所以能把「哪一段花多少时间」拆开量；下面所有数字都来自这套对照。
顺便说一句：web/whale 这个角色的**动画表现本项目没做任何降级** —— 弹簧、头发/裙摆/尾鳍摆动、
表情切换、被拎起来的挣扎、睡觉的 z、听你说话的弧线，全部照搬你们 figure.js 的算法重写的，
像素级对照过静止姿态。所以下面说的「省」，省的都是纯开销，不是画质。

二、实测数据
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
测试机：i7-6700（4 核 8 线程）/ 16 GB / Linux Mint 22.3 / X11 + xfwm4 合成器 / 核显+RTX 2060。
（这台机器上 QtWebEngine 拿不到硬件 GPU —— 日志里是「GBM is not supported, Fallback to
 Vulkan rendering」，所以 Chromium 那一侧是软件渲染，数字偏悲观；本项目要比的也是同一台机器。）

2.1 同一个核心、同一天背靠背量：两种宿主

                            本项目的 Chromium/QtWebEngine 宿主   本项目的原生宿主
    内存 RSS                626 MB                            195 MB
    内存 PSS（诚实口径）     503 MB                            149 MB
    进程数                  2                                 2
    其中核心                node 约 117 MB                    node 约 117 MB
    其中宠物端              约 509 MB                         约 78 MB
    CPU（60 秒 12 段）       平均 64.1%（50.4~80.6%）          平均 52.0%（19.0~82.2%）
    窗口出现                1.8 秒                            1.0 秒

    说明：Chromium 那一侧不管她在干嘛都是一条平线（浏览器恒定重绘整页）；
    原生宿主这边 CPU 是跟着「她在干嘛」起伏的（闲着 19%、溜达 82%）。

2.2 单帧的活是怎么分的（本项目把它移植过来之后逐段计的时）

    身体状态机（走/跑/跳/拎/坐/睡/眨眼/视线，对应 pet-core 的 createPet）   0.02 ms
    把姿势翻成骨骼参数 + 画那张 390×252 的脸（对应 figure.js 的 draw/paintFace） 0.70~0.85 ms
    17 块贴图按网格变形画上去（对应 rig.js 的 render）                      6.9~35.3 ms

    「网格」那一档对应不同的网格抽稀：不抽稀 547 格 = 35 ms，抽到 46 格 = 6.9 ms。

    说明：这三个数是本项目把同一套算法搬到 CPU 上画（Qt）时的成本，用来判断「哪一段的活重」。
    你们在 GPU 上画当然快得多 —— 但**「每帧把 752 个顶点各过一遍变形链」这一段的活，
    CPU/GPU 两边是一样的**（rig.js 的 applyChain + render 每帧都要跑），所以第 3 条的
    建议对你们同样成立；脸那一段更是纯 CPU 的活（canvas 2D）。

2.3 web/whale 这个 rig 的规模（你们自己最清楚，这里列出来是为了后面的建议对得上）

    17 块贴图、547 个网格格、752 个顶点、12 个枢轴点（pivots.body/waist/neck/armNear/...）
    最大的两块：hair_back 8×12（117 顶点）、bangs 8×10（99 顶点）
    每帧 rig.render() 会对这 752 个顶点各跑一次 applyChain()

2.4 帧率上限（原生宿主，一个核跑满时）

    不抽稀（547 格）        26.7 fps
    抽一半（148 格）        57.6 fps
    抽到 1/3（81 格）       90.2 fps
    抽到 1/4（46 格）      111.2 fps

    参考：把目标帧率设成 24 fps 时，CPU 只要半个核（57~64%）；48 fps 约 70%；60 fps 约 89%。

三、性能优化建议（按性价比排，都标了代码位置）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
★★★ 1. 脸部纹理别每帧「重画 + 重传 + 重建 mipmap」（figure.js:441-442 → rig.js:65-77）

    draw() 里每帧都做：
        paintFace(fc, face, o, t);
        rig.upload('faceFx', faceCv);
    而 rig.upload() 每次都会 texImage2D 之后再 **gl.generateMipmap()**（rig.js:71）。
    也就是说：**每帧一次 390×252 的整图上传，外加一整条 mip 链重建**。

    脸部贴图是要做显著缩小的（390 texel 最终画到几十像素），所以 mipmap 本身没毛病、
    别去掉；问题在「每帧重建一次」。建议分三档来做：
      · 参数没变 → 整段跳过（表情名 / 眼睛形状与尺寸 / blink / look 取整 / talk / blush
        做一次签名比对即可，绝大部分帧其实没变）；
      · 参数变了 → 只上传**真正变化的区域**（texSubImage2D 眼睛/嘴那两块包围盒，
        而不是整张 390×252），mip 只在换了表情（整张图都变）时重建；
      · 再进一步：把脸拆成「不动的底图 + 眼睛/嘴的独立小纹理」，底图只在换表情时更新。

    这条全平台通用。桌宠是常驻进程，省下来的是每秒 24~48 次整图上载 + mip 生成的持续开销。

★★★ 2. 静止的部件不用每帧重画（rig.js:142-179）

    render() 现在是无条件清屏 + 按 z 顺序重画全部 17 块。可实际上：
    站着不动的时候，真正在动的是头发、刘海、呆毛、尾鳍、脸；
    身体、裙子、鞋、发饰这些东西，除非在走/跳/被拎，否则一帧到下一帧几乎没差别。
    建议：把「连续若干帧变形量都小于半个像素」的部件渲染到一张离屏纹理上缓存，
    只在它的变形真的变了再重画。静态场景下能把 drawElements 的次数砍掉一大半。

★★ 3. 变形链里别每个顶点都新建数组（rig.js:121-139）

    applyChain() 每个顶点返回一个新数组 [x, y]，752 个顶点就是 752 次分配，
    48 fps 下大约每秒 3.6 万个小数组 —— 对 GC 不友好（桌宠是常驻进程，GC 抖动会看得见）。
    建议：传一个复用的 out 数组/两个数字变量，或者干脆把 applyChain 内联进 render 的循环里
    （热点就这一处，值得为它牺牲一点可读性）。

★★ 4. 加一个「闲时降帧」（全平台省电）

    现在页面是跟着 rAF 一直跑的，不管她在发呆还是睡着了。本项目实测：
    闲时把上限降到 12 fps、忙时 24 fps，CPU 直接省一半，肉眼几乎看不出差别
    （弹簧按 dt 积分，降帧只影响顺滑度，不影响动作幅度）。
    建议在 prefs 里加一个 `fps`（或者 `idleFps`），面板上给「省电 / 平衡 / 顺滑」三档。

★ 5. 超采样倍率别写死（figure.js:300-309）

    k = hypot(屏幕缩放) × devicePixelRatio × 1.25，画布边长按这个算（上限 6）。
    1.25 倍的超采样在软件渲染 / HiDPI 上代价是**面积级**的（1.25² ≈ 1.56）。
    建议把它做成常量或按平台能力自适应（拿不到硬件 GPU 时用 1.0）。

★ 6. preserveDrawingBuffer 别常开（rig.js:50）

    代码注释里写了：只有 `opts.raster`（把每帧拷进 SVG image 的那种模式）才需要它。
    常开会让浏览器多保留一份绘制缓冲，在部分驱动上会拖慢每帧的呈现。
    建议 `preserveDrawingBuffer: !!opts.raster`。

★ 7. drawFx 的字符串拼接（figure.js:459-496）

    好在最后有 `if (fx !== s)` 才写 DOM，这部分已经不错了；
    但每帧仍会为了比对而把所有特效 path 重新拼一遍字符串。
    可以给每种特效单独做个「值变了才重建」的小缓存（星星、听你说话的弧线、思考泡泡各自独立）。

（附：内建 Coo 图形那边还有一处更明显的：pet-core.js:951 每帧 `petG.innerHTML = figure(...)`，
  等于每帧重新解析一整棵 SVG。web/whale 走的是 canvas/WebGL 通道，所以不涉及；
  但如果想让内建形象也省，可以考虑改成复用节点只更新属性。）

四、一个会让角色「静默消失」的坑（建议加可见降级，比性能更值得改）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
如果 WebGL2 拿不到（显卡驱动黑名单、用户手动加了 --disable-gpu、远程桌面/虚拟机、
某些 Linux 发行版的默认配置），`createRig()` 会直接 `throw new Error('webgl2 unavailable')`，
于是 canvas 一直是空的 —— **角色整个人不见了，但 rAF 还在跑、帧率照样是 48 fps、
内存也确实降下来了**。光看指标完全发现不了，第一次遇到会以为是自己配错了。

本项目在移植过程中就被这个骗过一次（当时还以为「关掉 GPU 省了很多」）。
建议：
  · 在 createWhaleFigure() 里把 createRig 包一层 try/catch；
  · 拿不到 WebGL2 时给个可见的降级：画面里画一张静态的立绘（thumbs/ 里就有现成的图），
    或者至少把她的剪影画出来 + 控制台/面板上写清楚原因；
  · 顺手在「设置」里显示一行「渲染后端：WebGL2 / 软件 / 不可用」，排查起来会快很多。

五、文档/生态（第三方想接原生宿主时会卡在哪）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. `CORTICO_DESKTOP_PET_HOST` 很好用，文档也有（worlds.desktop-pet/README 第 61 行）。
   如果想让更多人做「别的宿主」（比如 Linux 上用 Qt、或者做成小挂件），
   可以把它单独提一节：宿主需要实现哪几个能力（透明置顶窗、光标位置、取屏做背景取样、
   装扮窗、气泡/输入的焦点接管……），最好配一张时序图。本项目是照着 preload.cjs 和
   外壳代码逆出来的，能逆出来纯属运气好。
2. rig 的规格值得正式写一页：`model.json` 里 `parts` 的 `box/grid/uvBox/alpha/z/parent`、
   `deformers` 的 `kind: rot|warp`（含 pivot/rect 与「子变形器先动」的次序）、
   `pivots`、`units.S/X0/FEET/DS/featDS`、以及贴名 `xxx@mix` 的交叉淡入约定。
   这些一旦公开，第三方就能做：新配色、新角色、甚至别的渲染后端（本项目就是照代码抄的）。
3. `schemes/<id>/tex + feat` 这套「同一套几何、只换贴图」的设计非常干净，
   建议在文档里给一个「照着 deepsea 做一个新配色」的最小步骤（复制目录 → 改 accent → 声明 ready）。

六、附：测试环境与复现方法
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
· 机器：i7-6700（4 核 8 线程）/ 16 GB / Linux Mint 22.3 / X11 + xfwm4 合成器。
  量的时候桌面上常驻着 Cherry Studio（约 40~60% 一个核）+ 火狐，load average 2.0~3.2，
  所以绝对数字偏悲观；但两组对照是**同一天背靠背**量的，横向比是公平的。
· 内存取 `/proc/<pid>/smaps_rollup` 的 Rss 与 Pss 之和（Pss 会把共享库按比例摊，更诚实）。
· CPU 取整棵进程树 `/proc/<pid>/stat` 的 utime+stime 增量，60 秒分 12 段采样。
· 帧率：把「忙时/闲时上限」设成同一个值，读进程自己每 5 秒输出的统计行；
  一共 14 秒热身 + 15 秒计时，同一档跑两次取区间。
· web/whale rig 的规模（17 块 / 547 格 / 752 顶点）是用 `model.json` 直接算的。

七、最后
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
整体上这个角色的完成度很高：程序化画脸（眼皮走 lidFit 那条折线、睫毛跟着压扁）、
头发/裙摆/尾鳍的弹簧、坐姿直接换一张裙子、配色用 @mix 交叉淡入 —— 这些细节看得出来很用心，
本项目在移植的时候基本是「照抄算法 + 只换渲染后端」，没有一处需要魔改才能跑。
上面那些建议只是「同样好看、但可以少烧点 CPU」的部分，供参考。

如果你们愿意，本项目这边写的原生宿主（Python + Qt，无 Electron）也可以整理出来给你们看 ——
它在同一台机器上把宠物端从约 509 MB 压到约 78 MB，代价是 CPU 要多花一点在网格上。
需要的说一声就好。
