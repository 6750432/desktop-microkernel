一、测的是什么、怎么测的
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
两条路线：
    老路线   = bash ~/coop-linux/启动.sh          （QtWebEngine 装网页，Chromium 底盘）
    原生路线 = bash ~/coop-linux/启动-原生.sh      （Python + QPainter，没有浏览器）

测法（脚本：`原生/量路线.py`，两条路完全同一套手法）：
    · 起脚本 → 每 0.25 秒问一次 wmctrl，记「窗口多久出现在 X 上」；
    · 等到第 40 秒（缓存/着色器都稳了）→ 采 **12 段 × 5 秒**（共 60 秒）；
    · 每段读整棵进程树的 /proc/<pid>/stat 算 CPU：**utime+stime 增量**（真 CPU，不是负载）；
    · 内存读 `smaps_rollup`：同时给 RSS 和 **PSS**。
      （RSS 会把共享库重复计，PSS 按比例摊，**PSS 才是诚实的内存数**）
    · 量完 killpg 整组收干净。

测试条件（很重要，这机器当时并不闲）：
    i7-6700 / 16G / Linux Mint 22.3 / X11 + xfwm4 合成器
    常驻：Cherry Studio（~40~60% 一个核）+ 火狐（~14%）+ Xorg（~10%）
    load average 2.0~2.4（8 线程），CPU 主频 3.4 GHz、powersave 调频
    → 所有绝对数字都偏悲观，但两条路是在同一条件下**背靠背**量的，横向比是公平的。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
脚本：`原生/量渲染.py`（用 thread_time 计时，不受别的线程干扰）
画布 217×217（缩放 0.62 × 1.25 超采样），17 块贴图：

  格步   身体.步   小鱼.画(含画脸)   网格.出图(骨骼变形)   一帧合计   24fps 折合 CPU
  1      0.02 ms   0.85 ms          35.33 ms             36.2 ms    87%
  2      0.02 ms   0.84 ms          13.91 ms             14.8 ms    35%
  3      0.02 ms   0.70 ms           9.01 ms              9.7 ms    23%
  4      0.02 ms   0.73 ms           6.86 ms              7.6 ms    18%

看得很清楚：
    · **身体状态机几乎不要钱**（0.02 ms/帧，跟网页版同一套算法搬到 Python）。
    · **画脸只要 0.7~0.85 ms**（每帧重画一张 390×252 的脸）。
    · **钱全花在「把他按网格变形画上去」**：格步 1 是 547 个小格，格步 4 是 46 个。
      这活儿原来是 WebGL2 干的（GPU 上一个 draw call 一批），现在 Qt 的 CPU 光栅
      一个一个格子来。这是 CPU 没像内存那样碾压的唯一原因。

  另外有个「程序里更贵」的现象（没查到底，但确实存在）：
      同一个函数在独立脚本里 9~16 ms，在开好窗口的程序里 15~27 ms（约 1.5~2 倍）。
      开窗前自检 13 ms、开窗后 25 ms。怀疑是合成器/X 抢缓存 + 和 Cherry Studio、
      火狐挤同一批核心。所有「程序里」的数字都按这个偏贵的情况算。

五、这一轮顺手修掉的一个 CPU bug
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
「睡着」原来比醒着还费 CPU（实测 58%）。
原因：睡觉时每 1.3 秒冒一个 z、飘 2.4 秒 —— 等于永远有粒子，而原先把「有粒子」当成了
「忙」，于是她睡着她还在满帧率画。改成「z 不算忙」（它飘得慢，12 fps 完全够看）之后：
    修之前：19~20 fps，58.4%
    修之后：11.6 fps，41.3%

六、跟老办法比，为什么内存赢这么多、CPU 只小赢
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
内存赢在「不用浏览器」：QtWebEngine 就算开空页、单进程、关掉所有缓存，
地板也是 **383 MB**（之前实测过）。原生的宠物端自己只有 78~84 MB，
剩下的就是 Python + Qt 的本体。

CPU 赢不动，是因为瓶颈换人了：
    老办法：CPU 花在 Chromium 的合成/光栅/GC 上，恒定开销（跟她在干嘛无关）；
    原生：  CPU 花在「Python 每帧拼 46~547 个小格子」；
            好处是**能按需降档**（闲时 12 fps、格步调粗），坏处是单帧成本比 GPU 高。
换句话说：内存是一次性省下来的，CPU 是「省一半 + 剩下那半可以随时再调」。

七、还想再压 CPU 的话，按性价比排
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. **整块部件合并绘制**（最值）：手臂、腿、尾巴、鳍、呆毛这些只受「旋转/缩放」的
   部件，整块就是一个仿射变换，现在却被拆成几十个小格分别画。合并后估计再省 20~30%。
2. **空闲再降一档**：现在闲时 12 fps，可以视情况给 8 fps（睡着/坐着时人眼看不出）。
3. **窗口再收小**：现在 360×360，里面有相当一部分是透明边缘；收到 300×300 能省一点贴图开销。
4. **少抽一点超采样**：现在是 1.25 倍超采样（0.775 像素/单位），改成 1.0 倍能省约 1/3 像素量，
   代价是边缘略糙。

九、补测：原生 Qt 到底能跑多少帧？（同日 21:35~21:58）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
脚本：`原生/量帧率.py`（把闲时帧率设成跟忙时一样，关掉自适应，免得降帧掺和）

先修了一个**节奏 bug**（不然下面所有数字都不准）：
    原来「打点」和「出画」共用一个定时器，打点间隔 8 毫秒 → 帧周期被**向上取整**到
    8 的倍数：目标 60 fps（16.7 ms）只能到 24 ms = 41.7 fps，目标 24 fps 只能到 18~22。
    改成「高频打点（只管问光标/写统计）+ 单发定时器出画（按上一帧开始时间 + 目标间隔
    排下一帧）」之后，目标多少就是多少：目标 24 → 实测 24.0；48 → 46.6~48.0；60 → 58.9~59.2。

① 天花板（不设上限，一个核跑满，CPU ≈ 99~111%）

    画质档               格子数    实测最高帧率   每帧重绘    CPU
    格步1（最细）         547      26.7 fps      35.0 ms    98.8%
    格步2                 148      57.6 fps      13.5 ms   101.8%
    格步3（默认）          81      90.2 fps       8.6 ms   107.7%
    格步4（最省）          46     111.2 fps       6.3 ms   111.1%
    格步3 + 小个子(0.42)   81     103.0 fps       7.3 ms   102.4%

    → **这台机器上原生渲染的天花板是 27~111 fps**，取决于画质档。
      再往上只能靠「把网格分给多个线程画」（Qt 这段是单线程的，机器有 8 个线程可用）。

② 跟着目标帧率走的实测（同样的桌面负载，load ≈ 2~3.2，每组两次）

    目标      实测              CPU              备注
    24 fps   24.0 / 23.9 fps   57.4 / 63.8 %    默认就是这档（闲时再降到 12）
    48 fps   46.6 / 48.0 fps   74.9 / 67.6 %    性价比最好的一档
    60 fps   59.2 / 58.9 fps   90.5 / 88.8 %    格步3 也能上 60，但要吃掉将近一个核
    60 fps   57.3 fps          83.5 %           改用格步4，同样的 60 省 5~7 个点

③ 给用户的一句话建议
    · 默认那档（忙 24 / 闲 12）是**省电档**，CPU 平均只占半个核，日常挂着最划算；
    · 想看着顺：`COOP_FPS=48`（实测 46~48 fps、CPU 约 70%），比 60 便宜不少；
    · 真要 60：`COOP_GRID=4 COOP_FPS=60`（57 fps / 83.5%）；别用格步1，那档只有 27 fps。

④ 为什么「低帧率反而每帧更贵」：同一档画质，目标 24 fps 时每帧重绘 15~19 ms，
   目标 60 fps 时只要 ~10 ms —— 两帧间隔越长、她位移越大，要重画的区域
   （新旧位置并集）也越大。所以降帧省的是总 CPU 时间，但单帧并不便宜。

十、补测：原生 QPainter 的「理论值」到底是多少（同日 22:10~22:20）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
脚本：`原生/量理论.py`（分三层量：光栅器本身 → 一次绘制调用的固定开销 → 整帧两种画法）

① QPainter 光栅器本身有多快（往 ARGB32 图上画，217×217 画布）

    填充整块矩形            0.009 ms   ≈ 4980 M像素/秒
    1:1 贴图                0.017 ms   ≈ 2800 M像素/秒
    512×512 缩到 217×217    0.022 ms   ≈ 2180 M像素/秒（双线性）
    64×64 放大到 217×217    0.025 ms   ≈ 1910 M像素/秒（双线性）

    她那一帧真正要涂的像素只有约 3 万个（她整个人占的那一小块），
    → 纯像素成本 ≈ 0.01~0.06 ms/帧。**光栅器快得不值一提，理论上几万 fps。**

② 一次「绘制调用」的固定开销（这才是真花钱的地方）

    只 setTransform + drawImage                13 µs/次
    + 矩形裁切                                  10 µs/次
    + 路径裁切                                  19 µs/次
    + 路径裁切 + save/restore（现在就是这么写的）  18 µs/次
    + 再加一次 quadToQuad（现在也是每次现算）      22 µs/次

    Python 那一侧（造 2 个 QPolygonF/8 个 QPointF + 撑边用的 QPainterPath）  17 µs/格
    → 理论上「一格的成本」≈ 39 µs；实测每格 ≈ 57~67 µs，
      多出来的约 25 µs 是真实数据才有的开销（752 个顶点过变形链、以及在大贴图上采样时的缓存不命中）。

③ 整帧两种画法对比（同一姿势、同一画布）

    现状：逐格裁切                 547 格 → 36.5 ms/帧 → 理论上限  27.4 fps
    合并：每块部件一次绘制          17 块 →  0.23 ms/帧 → 理论上限 4300 fps
    现状：逐格裁切（抽稀到 1/4）    46 格 →  7.0 ms/帧 → 理论上限 142.6 fps
    合并：每块部件一次绘制          17 块 →  0.29 ms/帧 → 理论上限 3400 fps

    （「合并」这一档只量「一次绘制的价格」，形变是忽略的 —— 它回答的是
      「如果每块部件只发一次绘制调用，光栅这一层的上限在哪」，不是「这样画好看」。）

④ 把网格抽到只剩每块 1 格（≈17 次绘制）时的**整机实测**上限

    目标 240 fps → 实测 145.6 fps（CPU 114.2%，重绘 4.4 ms/帧）
    目标 144 fps → 实测 139.0 fps（CPU 113.2%）

    → 也就是说：**就算网格的开销归零，这台机器也只到约 145 fps**，
      被「窗口贴图 + 合成器 + 一个多核的 CPU」卡住；而屏幕本身是 144 Hz，再高也看不出来。

⑤ 结论：分三层看「理论值」

    层                          上限
    光栅器（纯像素）            几万 fps（500~2800 M像素/秒）
    每块部件一次绘制（光栅层）   3400~4300 fps
    整机（窗口+合成器+CPU）      **约 145 fps**（实测）
    屏幕                        144 Hz（再高没意义）
    现在这条实现（逐格裁切）     26.8~142.6 fps ← 距整机上限还有约 1 倍空间

    → 一句话：**QPainter 本身不是瓶颈，本项目自己的「每格一次调用 + 每格现造 Qt 对象」
      才是。** 现在离这台机器的真实上限（145 fps）大约差一倍；
      把②③里那些固定开销压下去（合并仿射部件、矩形裁切代替路径裁切、
      每格的 QPointF/QPolygonF 跨帧复用），满画质的下限也能从 27 fps 抬到接近 100 fps。

（这一节先做了一个**能跑的原型**再给数字，不是纸上算；原型脚本：`原生/量快版.py`）

11.1 已经验证的一步：不改画质，去掉实现里的浪费 → **1.4~1.8 倍**

    原型做了三件事（都不改画出来的东西）：
      ① 源多边形（贴图坐标）每帧都一样 → 预先算好（省一个 QPolygonF + 4 个 QPointF/格）
      ② 裁切从「路径裁切」改成「四边形外接矩形裁切」（省 QPainterPath 和往外撑的浮点运算）
      ③ 只受旋转/缩放的 5 块部件（手臂、两条腿、躯干）整块一次画完 —— 数学上是精确等价的

    画法           格步1（547 格）        格步2（148 格）       格步3（81 格）
    现状           36.4 ms → 27.5 fps     13.0 ms → 77.1 fps    8.9 ms → 113.0 fps
    快版 A         20.1 ms → 49.7 fps      8.3 ms → 120.9 fps    6.2 ms → 160.6 fps
    快了多少       1.81 倍                1.57 倍               1.42 倍

    画质核对（快版 A 与现状逐像素比，格步1）：
        完全相同 90.66% ｜差 1~8 级 7.72% ｜差 9~32 级 1.53% ｜差 33~64 级 0.09% ｜≥65 级 2 个像素
        差异全在格子接缝的半像素抗锯齿上（肉眼无差别；放大 6 倍逐格看过手、脸、裙摆）。

    ⚠️ 踩到的坑（两个都是「看起来更快的写法其实是错的」，靠逐像素比对才发现）：
      · 设裁切之前**必须把变换复位成单位矩阵** —— 否则裁切矩形会被上一格的透视矩阵搬走，
        结果几乎什么都没画出来（但帧率漂亮得吓人：快了 2 倍）。
      · 整块仿射时，网格的「左下角」是 `ny*(nx+1)`，不是 `nx+1`（那是第二行）。

11.2 再往下的两步（还没做，按已量到的常数估）

    ④ 每格的 QPolygonF/8 个 QPointF 跨帧复用（改成 replace() 就地更新）
       现在每格约 43 µs，其中造对象约 8~9 µs、Qt 调用（裁切+变换+贴图）约 10~13 µs。
       估再省 **1.3~1.5 倍**。
    ⑤ 增量渲染：只重画「这一帧真的变了」的部件（头发/刘海/呆毛/脸），
       身体、裙子、鞋这些静止时直接复用上一帧的图层。
       静止时可省 **60~80%** 的工作量（走、跳、被拎时照旧全画，不影响观感）。

11.3 不改画质的「极致」预估（把 ①~⑤ 都做完）

    画质档                现在（实测）        做完之后（预估）
    格步1（最细，547 格）  27 fps              **50~70 fps**
    格步2（148 格）        77~121 fps          **顶到屏幕**
    格步3（默认，81 格）   90~145 fps          **顶到屏幕（144 fps）**
    巡航 CPU（24 fps）     57~64%              **约 25~30%**
    巡航 CPU（60 fps）     89~91%              **约 40~45%**

    注意：天花板是**屏幕的 144 Hz**（实测把网格抽到最少时整机也只能到 145.6 fps）。
    所以「极致」的终点不是帧率，而是「144 fps 下 CPU 最低」。

11.4 换渲染骨架之后的预估

    (a) 多线程光栅：17 块部件分给 2~4 个线程各画到独立图层再合成。
        这台机器 8 线程、现在只用了一个多一点。理论 ×3~5，实际受合成与内存带宽限制，
        估 **×2.5~3.5** → 满画质（格步1）从 50~70 抬到 **150 fps 以上（屏幕封顶）**。
        代价：内存 +20~40 MB（每线程一张图层），CPU 总量不变（只是摊到多个核上）。
    (b) GPU 后端（QOpenGLWidget + 上游 rig.js 那套着色器）：网格变形交给 GPU，
        CPU 只更新顶点缓冲。→ **任何画质都是 144 fps（屏幕封顶），CPU 从 30~50% 降到 3~8%**。
        风险：本机 QtWebEngine 拿不到硬件 GPU（GBM 不支持，回退软件渲染）；
        但 PySide6 自己的 QOpenGLWidget 走的是 GLX/NVIDIA 驱动，通常能拿到真 GPU —— 要实测才算数。
    (c) 组合 (b)+(c 增量)：**144 fps + CPU 个位数百分比**，这才是这条路的真正终点。

11.5 一句话给用户
    · 不改画质、只去浪费：**满画质 27 → 50~70 fps**，默认档直接顶到屏幕 144 fps，巡航 CPU 减半。
    · 换 GPU 骨架：**144 fps 封顶 + CPU 个位数**。
    · 原型已经跑通并逐像素验过，随时可以落地到 `网格.py`（留一个开关，出问题一键回退）。
