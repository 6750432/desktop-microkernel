Cyber-Microkernel Runtime v7.0
—— v2 之后又走了五代：它会变成什么样
2026-09-29  Coopanion Native Host

【先认错】上一版写错了：把 v7 写成了「v2 + 三平台矩阵」，那其实是 v2.1（已改名
`Cyber-Microkernel-v2.1-三平台增补-2026-09-29.txt`，内容是 v7.0 的一个子集，留着当附录用）。
v2 → v7 是**五次迭代**，每次迭代都由"上一代在真机上暴露的问题"逼出来。
这一版写的是**那条演化路径本身**，以及走完五代的 v7.0 长什么样。

      v3 把纪律变成机制 → v4 把平台变成数据 → v5 把性能变成闭环 →
      v6 把故障变成可复现 → v7 把宿主变成可替换的插件。

一、v3「机制期」：把纪律变成会自己执行的机制
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【上一代暴露的问题】
    · v2 的预算表是"文档里的门槛"：没人守，超标了也不知道；CI 只跑功能不跑性能。
    · 降级发生在用户机器上，而本项目只能事后猜——**静默失败**（渲染后端拿不到但指标全绿）
      第一次出现就说明："能跑"和"跑对了"是两件事。

【这一代引入的机制】
    1. **帧预算管理器（FrameBudgetManager）**：预算不再是文档，而是运行期对象。
       每帧记录 tick/present 两段时间 + 跨界调用次数 + 新建对象数；
       滑动窗口（300 帧）算 p50/p95；**超预算连续 N 帧 → 发事件**（不是打日志了事）。
    2. **降级档案（Degradation Ledger）**：每次降级写一条带时间戳的记录（哪个能力、哪个后端、
       什么错误码、怎么恢复的），**跨会话持久化**。下次启动时先读档案：
       "这台机器上 GPU 后端失败过 2 次（TCC/驱动），本次直接走 software"，
       并给档案一条 TTL（驱动/系统更新后作废，重新上探）。
    3. **健康三问变成一等公民**：输入区/呈现/资源，每 10 秒一次，
       失败不再只是日志，而是**触发降级 + 记档案**。
    4. **验收脚本进 CI 的门**：`tools/验收.py` 的 JSON 输出成为合并门槛；
       没有数字的功能改动不允许合并（这一条比任何架构图都管用）。

【删掉】文档里的"预算表"（保留为仪表盘视图）；"人肉看日志判断有没有退化"。

【门槛（进入 v4 的条件）】单平台（Linux/X11）上：预算全绿、健康三问全绿、降级档案能跨会话生效。

二、v4「平台数据期」：把平台差异从代码里赶出去，变成数据
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【上一代暴露的问题】
    · 想验 Windows/macOS 的降级路径，手上只有一台 Linux —— 只能靠"读代码觉得没问题"。
    · 平台分支开始往核心渗（"这里 Windows 要这样、那里 Wayland 不行"）。

【这一代引入的机制】
    1. **十二个能力位**（事实由探测给、能力由策略表推）：can_open_display / can_make_transparent /
       can_set_input_region / can_hit_test_per_pixel / can_always_on_top / can_skip_taskbar /
       can_position_window / can_query_pointer / can_receive_global_input / can_capture_screen /
       can_join_all_spaces / can_exclude_from_capture。
    2. **SIMULATE 模拟矩阵**：`SIMULATE=no_compositor,no_input_region,no_position,...`
       —— 不是 mock 后端，而是**同一个后端的能力位被置否**，策略层与降级链走真实路径。
       **一台 Linux 压完三平台 80% 的降级逻辑**；真机只验"实现对不对"。
    3. **后端插件契约（声明式）**：每个后端自带一份 `backend.json`：
       声明它提供哪些能力位、依赖什么权限、自检怎么做、出错码前缀。
       核心只看声明，不 import 具体后端 → 后端可以来自第三方（本项目昨天写的那个宿主就是。
    ⚙ **这条是"微内核"真正的含义**：内核只认契约，皮（宿主/后端）随便换。
    4. **铁律 5 上线**：核心代码里禁止出现平台名，CI 用一行 grep 守住。

【删掉】写死的后端清单、`if 平台` 分支、"抽象到零平台代码"的幻想（抽象不了的就用能力位显式降级）。

【门槛】三平台（或"一真机 + 两组 SIMULATE"）上：降级链 100% 覆盖、`grep` 守卫生效。


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
三、v5「性能闭环期」：从"手调档位"到"自己调"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【上一代暴露的问题】
    · CPU 光栅到顶：把渲染压到几乎为 0，整机也只有 145.6 fps（单核 114%）——
      **窗口贴图+合成器就是 4~5 ms/帧的地板**；而满画质一帧 36.4 ms。
    · 画质档（网格抽稀、缩放、帧率）要人去手调；不同机器上"合适的档"完全不同。
    · 每一帧都在全量重绘，哪怕她只是站着呼吸。

【这一代引入的机制】
    1. **多后端并行**：同一帧按图层/部件分给 2~4 个 Worker，各自渲染到独立图层再合成；
       准入条件（用数据说话）：单线程 p95 > 目标帧时间 ×1.2、跨界调用数已达标、
       Python 侧纯计算占比 > 40%。
    2. **增量渲染**：脏区 + 图层缓存 —— "这一帧变了什么就重绘什么"。
       静止时把不变图层直接复用（⚙ 本项目实测：合成绘制只要 0.23 ms，所以"少画"就是纯赚）。
    3. **自适应画质（预算驱动）**：帧预算管理器给出 p95 超标 → 自动降档（抽稀/降帧/关特效），
       留档并上报；恢复也要有"回升"策略（避免抖动：升档要连续 N 秒达标）。
    4. **帧源统一**：拿不到真 vsync 时用"高精度定时器 + 自适应周期"，并把帧源写进指标。
    5. **闲置三段**：活跃/低动/静止；判据是"**画面真的变了多少**"，
       ⚠️ 不是"有没有东西在动"（本项目踩过：睡觉的 z 粒子让她睡着最费 CPU，58%）。

【删掉】固定的画质档位表、"整帧重绘"、单线程假设（线程从"设计假设"变成"运行时决策"）。

【门槛】同一份 `验收.py` 在**三档硬件**（强/中/弱）上跑出预算内结果；
      自适应降档在人为造超预算（SIMULATE=slow）时能自动触发且不抖。

四、v6「可复现期」：故障从"猜"变成"回放"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【上一代暴露的问题】
    · 偶发问题（切 Space 后消失、插拔显示器后错位、跑两小时后卡）根本复现不了；
      日志是散文，只能靠时间戳拼。
    · 每次启动都去撞一次已知失败（驱动黑名单里的 GPU、没授权的取屏），
      用户每次都要等一次超时。

【这一代引入的机制】
    1. **可回放事件流**：所有输入事件（系统事件、配置变更、随机种子、时间步长）
       写成**确定性事件流**；给定事件流 + 种子 → 能重放出同一串帧。
       故障排查从"再试一次"变成"把事件流发过来"。
    2. **故障快照包（crash/diag bundle）**：出问题时自动打包
       最近 N 秒事件流 + 当前能力位 + 后端与版本 + 指标摘要 + 健康三问结果（脱敏）。
    3. **监督进程 / 自愈**：核心与宿主分离，宿主崩了自动拉起（状态机在核心侧，不丢）；
       后端反复失败 → 降级档案生效，不再撞。
    4. **协议版本协商**：宿主 ↔ 核心的 WS 协议带 `proto_version` + 能力协商；
       双方各自声明支持的最小/最大版本，不认识就明确报错（而不是静默半通）。
    5. **长跑看护**：24 小时曲线的自动断言（内存斜率、句柄数、p95 漂移、降档次数）。

【删掉】"重启试试"这类排查话术、散文式日志（保留人读视图，但**机器读的一律 JSON**）、
        "每次启动重新试探所有后端"。

【门槛】把过去三个月的偶发故障各重放一次，能复现 ≥ 80%；长跑 24 小时曲线三条全平。

五、v7「插件期」：宿主是可以换掉的皮
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【上一代暴露的问题】
    · 宿主把核心拖死过（宿主崩溃/卡死连累状态机）；
    · 本项目想用 Python 写宿主、别人想用 Rust/C++/Swift 写；第三方想加自己的后端；
    · 笔记本用户抱怨耗电：桌宠整天空转。
    · "微内核"这个名字还只是分层图上的说法，没有真正兑现。

【这一代引入的机制】
    1. **核心 / 宿主彻底分离**：内核只负责状态机+动画+场景图，输出 RenderList；
       宿主是一层可替换的皮（渲染/窗口/输入/装饰）。**换皮不需要动内核**（本项目已经验证过一半：
       把网页宿主换成 Python 宿主，核心一行没改）。
    2. **IDL 化的宿主契约**：接口用一份语言中立的描述文件定义（能力位声明 + 消息集 + 错误码 +
       自检要求），任何语言都能生成桩；附带一个 **"宿主一致性测试"**（跑一遍就知道你这层皮合不合格）。
    3. **能耗一等公民**：把电量/温度/前台有没有人当输入；
       闲置三段 + 屏保/锁屏/全屏游戏时自动"隐身降档"（并可配置为完全休眠）。
    4. **信任链与交付**：签名（Windows）/ 公证（macOS）/ Flatpak 权限清单（Linux）+
       SBOM（依赖清单）+ 可复现构建（同源码同产物）+ 更新通道（后端插件可独立更新）。
    5. **多宿主并存**：同一内核可以同时被"桌面宠物宿主""挂件宿主""控制台调试宿主"连接，
       能力最全的那个拿到"主控"，其余只读（这解决了"调参时想同时看两边"的问题）。

【删掉】"宿主是一等公民"（宿主降级为皮）、单语言假设、单一交付形态、
        把能力位写进内核的任何残留。

【门槛（7.0 的发布线）】三平台一致性测试全绿 + 预算表全绿 + 长跑曲线全平 +
       第二语言宿主（哪怕最小实现）通过一致性测试 + 信任链三件套齐。

六、v7.0 终态：只有跑了几代才长得出来的七个机制
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
（前面是"怎么长出来的"，这一节是"长成什么样"。这七个是 v2 完全没有的。）

    ① 帧预算管理器        预算从文档变成运行期对象；超预算 → 事件 → 自动降档 → 记档案。
    ② 降级档案（跨会话）    踩过的坑不再踩；带 TTL，环境变了自动重新试探。
    ③ 自适应画质           预算驱动，升档要连续达标（防抖），降档要立刻（保命）。
    ④ 可回放事件流 + 快照包  偶发故障可复现；用户点一下就能生成诊断包。
    ⑤ 监督进程 / 自愈       宿主崩了自动拉起，状态机不丢。
    ⑥ 后端与宿主插件化      能力位 + 自审 + 一致性测试；第三方可写（本项目就是这么干的）。
    ⑦ 协议与交付的版本化     proto_version 协商 + SBOM + 可复现构建 + 更新通道。

    另外三条"看起来小、其实最省事"的：
    · **一行一 JSON 的日志**（机器可读，人也能看）；
    · **能力位驱动的一切降级**（没有 if 平台）；
    · **验收脚本是唯一的真相**（架构图再漂亮，跑不出数字就是没做到）。

七、验证金字塔（v7 的测试长这样）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    第 1 层 单元        ：策略表逐行断言（能力组合 → 策略）；探测器用假事实注入。
    第 2 层 模拟（SIMULATE）：8 组能力缺失 × 每个后端 FORCE_FAIL，全部走真实降级路径。
    第 3 层 真机冒烟     ：每平台 10 条（起/透明/穿透/拖动/置顶/不进任务栏/切桌面/
                          插拔屏/待机降档/退出干净），10 分钟跑完。
    第 4 层 长跑         ：24 小时曲线（内存斜率、句柄、p95 漂移、降档次数）。
    第 5 层 回放         ：把历史故障事件流丢进重放器，断言"同样的帧序列"。
    ⚠️ 五层里只有第 3 层需要真机 —— 这就是 SIMULATE + 事件流换来的自由度。

八、如果上游今天只有 Electron：从哪代切入最划算

    · **最划算：先做 v3 的两件小东西**——帧预算管理器 + 验收脚本。
      不用动架构，就能让"退化"看得见；Electron 侧同样适用（本项目量到的地板 4~5 ms/帧、
      每帧固定开销这些数字，对任何浏览器宿主都成立）。
    · **第二步：v4 的能力位 + SIMULATE**。让"Linux 上跑什么样"不再靠猜；
      顺带把"窗口能力缺失怎么降级"写进产品行为。
    · **第三步（可选）：v7 的宿主松耦合**。上游只要把"宠物窗口"那一侧定义成可替换的皮
      （已经有 `CORTICO_DESKTOP_PET_HOST` 这个口子了），第三方宿主就会长出来 ——
      本项目那份 AppImage 就是一次现成的验证：核心一行没改，宿主端内存从 509 MB 降到 78 MB。
    · **不建议一上来做 v5/v6**：多后端并行、事件流重放都建立在前几代的度量与契约之上，
      跳过它们会变成"为复杂而复杂"。
