一、目标与非目标
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
目标（一句话）：
    让「宠物窗口」这一层在任意桌面环境下**都能起来、都能降级、都能自证**，
    并且**核心逻辑（状态机/动画/场景图）永远不感知平台**。

非目标（V0.2 明确不做，做了就是负债）：
    · 不做 GPU 后端（QRhi/Vulkan/D3D）、不做 Wayland/DComp 后端；
    · 不做 ILifecycle / 引用计数 / 弱引用缓存（没有热切换就没有多次 acquire/release 的需求）；
    · 不做异步探测（同步探测 50 ms 以内就够，异步只增加状态机复杂度）；
    · 不做 Metrics 对外通道（Prometheus/OTel）——只写 JSON 日志；
    · 不做「脱离 Qt」的评估 —— 那是 V0.4 的调研项，不是设计约束。

判据（什么时候才允许把上面某条捡回来）：**§3 的预算表里某项超标、且 §7.2 的健康三问无法解释**。

二、四条铁律（全部原则压缩成四条，只说一次）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
铁律 1｜**探测给事实，不决策。** 策略只能出现在策略表里（§5.2），不能出现在 if 里。
铁律 2｜**热路径只花预算，不花判断。** 每帧允许做的事，在 §6.1 写死；越界的写法一律不进热路径。
铁律 3｜**任何"降级"都必须可解释、可测量。** 降级要打一条 JSON 日志 + 一个指标；没有数字的降级 = 故障。
铁律 4｜**退出严格反序，且退出阶段不再创建任何 Qt 对象。**

（v1.3 里「接口层禁止暴露 Qt 类型」保留，但改成可执行的形式：
  见 §6.1 —— 不是"禁止"，而是"跨界调用有次数预算"。禁止在 Python 里做不到，预算才管得住。）

三、预算表（验收口径；所有设计都对着它）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
⚙ 先说一个必须知道的事实（本机实测，i7-6700 / X11+xfwm4 / 144 Hz）：
    · 把渲染压到几乎没有（≈17 次绘制调用），整机也只能 **145.6 fps**，CPU 已 **114%**；
    · 也就是说 **「窗口贴图 + 合成器」是 4~5 ms/帧的硬地板**，与画什么无关；屏幕只有 144 Hz。
    · **结论：不要再用绝对 FPS 当验收**（196 fps 在这台机器上物理不可达）。
      绝对 FPS 会被"帧率上限"和"地板"两头夹住，优化了也看不出来。

    ┌────────────────────────┬─────────────┬──────────────────────────────┐
    │ 指标                    │ 门槛        │ 怎么测                        │
    ├────────────────────────┼─────────────┼──────────────────────────────┤
    │ 帧时间 p50 / p95        │ ≤ 预算×0.6 / │ 每帧两点：tick 开始 → present │
    │ （在目标帧率下）         │ ≤ 预算×1.0  │ 完成；写 JSON，滚动 300 帧算  │
    │ CPU：24 / 48 / 60 fps   │ ≤ 0.6 / 0.8 │ /proc 整棵进程树 utime+stime  │
    │                        │ / 1.05 核   │ ÷ 真实流逝时间                │
    │ CPU：闲置（目标 12 fps） │ ≤ 0.15 核   │ 同上，且"闲置"要有定义（§6.4） │
    │ 内存 RSS / PSS          │ ≤ 250 / 180 MB │ smaps_rollup 求和（PSS 更诚实）│
    │ 冷启动 → 首帧           │ ≤ 1.5 s     │ 进程启动到第一次 present 返回  │
    │ 回退链完整性             │ 100%        │ 每个后端 FORCE_FAIL=1 注入一遍 │
    │ 健康三问（§7.2）         │ 全绿        │ 每 10 s 一次，失败即降级        │
    └────────────────────────┴─────────────┴──────────────────────────────┘

⚙ 本机参考值（原生宿主实测，用来判断"离目标还有多远"）：
    内存 RSS 195 MB / PSS 149 MB；冷启动 1.0 s；
    CPU 24 fps 巡航 57~64%｜48 fps 68~75%｜60 fps 89~91%（一颗核跑满 ≈ 100%）；
    帧时间（同一台机器、同一画质档）：网格 9 ms、合并绘制后 0.23 ms。

四、分层与责任（边界表保留，只补三行）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    | 模块 | 输入 | 输出 | 严禁做的事 |
    |------|------|------|------------|
    | PreProbe | 系统调用 | ProbeResult（部分） | 不做决策、不依赖 Qt |
    | PostProbe | Qt 屏幕 API | ProbeResult（显示） | 不做决策 |
    | CapabilityResolver | ProbeResult + 导入期常量 | CapabilityBits | 不读用户偏好、不选后端 |
    | ConfigResolver | CapabilityBits + 用户偏好 | RuntimeConfig | 不实例化后端 |
    | BackendFactory | RuntimeConfig | BackendBundle | 不在运行期被频繁调用 |
    | IRenderer | RenderList | NativeSurface | 不判平台、不自己创建窗口表面 |
    | IPlatformBackend | 事件 / vsync | NativeSurface | 不管渲染算法 |
    | FrameScheduler | Vsync | tick 信号 | 不跑核心逻辑 |
    | InputRegion | 鼠标事件 + 当前帧轮廓 | 命中结果 | 不判平台 |
    | ScreenDpi | 屏幕事件 | DPI / 缩放 | 不重建后端（判据见下） |
    | ILogger | 日志调用 | 输出流（JSON 行） | 不依赖 Qt、不在热路径打日志 |
    | Metrics | 埋点事件 | 指标数据 | **不在热路径做字符串拼接/分配** ← 新增 |
    | HealthCheck | 低频心跳 | 健康事件 | **不直接改后端状态，只能发事件** ← 新增 |
    | SelfCheck | 当前帧 + 系统状态 | 健康结论 | **不得依赖后端"自报成功"** ← 新增 |

    两条模糊处补判据：
      · ScreenDpi 何时允许重建：**仅当缩放比变化 > 5%，或跨屏导致 surface 失效**；
      · BackendFactory 何时允许再调用：**只在启动、热切换、HealthCheck 升级事件**这三种时刻。

五、启动：四段式（Probe → Capability → Policy → Factory）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
5.1 事实与能力位

    ProbeResult（纯事实，v1.3 的字段基本保留，命名统一后缀）：
        环境：os_family / session_type / is_remote / sandbox_type / sandbox_grants(frozenset)
        CPU ：cpu_cores / cpu_clock_hz / clock_resolution_ns
        GPU ：gpu_present / gpu_vendor / gpu_driver / gpu_api_support(list)
        显示：monitor_count / primary_dpi_scale / primary_refresh_hz / work_area_margin
        ⚙ 新增（**比 GPU 更容易翻车的四个窗口层能力位**，同样是事实不是策略）：
              can_open_display        能不能连上显示服务（沙箱里可能直接失败）
              can_set_input_region    能不能设输入区形状（设不了就退化成整窗吃鼠标）
              can_query_pointer       能不能全局查光标位置（"看向鼠标"靠它）
              can_always_on_top       能不能置顶 / 不进任务栏 / 不抢焦点
        ⚙ 说明：这四个失败时的表现是「**看起来在跑，但点不到/看不到/穿不过去**」，
          比 GPU 失败难查得多 —— 必须显式探、显式降级、显式打日志。

    ProbeDiagnostics（诊断数据，与事实**分开**——避免把"探测超时"当成"没有 GPU"）：
        total_duration_ms / probe_timeout / sub_probe_status{"GpuProbe":"ok","DisplayProbe":"timeout"}
        ⚙ 输入只允许给日志与 Metrics，**禁止进策略**：事实、诊断、能力，三层严格分开。

    CapabilityBits（能力抽象，不出现平台名）：
        render_backend_hint  gpu | software        （hint：只给 Factory 参考，不是事实）
        partial_update       bool                  （能否只更新脏矩形）
        region_input         bool                  （能否用形状做输入区）
        vsync_source         str                   （x11_present / dwm_flush / displaylink / timer）
        thread_budget        int
        refresh_hint         float
        dpi_hint             float
        ⚙ 命名纪律：`*_hint` 一律是提示、`*_grant` 是沙箱给的许可、其余无后缀的才是事实。
          下游如果把 hint 当事实用，就是这层设计出了问题。

5.2 能力 → 策略：写成表，不写进 if

    | 能力组合                                  | 策略                                          |
    |------------------------------------------|-----------------------------------------------|
    | region_input=true                        | 输入区用系统形状；否则退到"窗口级"（整窗吃鼠标）   |
    | partial_update=true                      | 走脏矩形局部重绘；否则整帧重绘                   |
    | gpu 可用 且 user=auto/gpu 且 is_remote=false | renderer=gpu                                |
    | is_remote=true 或 gpu 连续失败 ≥2 次       | renderer=software（并记一条降级日志）           |
    | sandbox_grants 含 vulkan/gl 但 can_open_display=false | 仍然是 software（显示层优先于 GPU）    |
    | refresh_hint ≥ 120 且 CPU 预算充足         | 目标帧率 60；否则 30                            |

    ⚙ 落笔要求：这张表就是策略层**全部**的内容；`if` 只允许出现在"查表"这一处。

5.3 回退链与错误分类（保留 v1.3，补两条）

    BackendError: { error_code, recoverable, context }
    错误码分类 → 跳过范围：
        gpu_*        → 跳过所有 GPU 后端
        display_*    → 跳过当前显示服务后端
        permission_* → 跳过同类权限受限后端
        input_*      → **只降级输入方式（形状→窗口级），不换后端** ← 新增（输入区失败不该拖垮整链）
        present_*    → 当前后端仅降级刷新策略，连续 2 次才升级为换后端 ← 新增

    ⚙ 两条 v1.3 没写清的：
      ① 「跳过」的有效期：**默认到本次会话结束，或下一次 ReProbe 为止**（写进日志，别默认永久）。
      ② 每个后端必须支持 FORCE_FAIL=1（**架构级要求，V0.2 必做**，不是测试细节）：
         本项目的真实教训是"**WebGL2 拿不到 → 角色静默消失，但帧率/内存指标全都正常**"，
         只有注入式失败 + 自检才能把这类故障钉在 CI 里。

六、运行期：主循环、预算、线程、输入区
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
6.1 每帧只花两条预算（这是全文最值钱的一条）

    ⚙ 实测（同一帧、同一画质，217×217 画布）：
        逐格裁切：547 格 → **36.4 ms**（一颗核跑满，27 fps）
        合并绘制：17 块 → **0.23 ms**（光栅层快 150 倍；逐像素比过，90.7% 完全相同）
        其中：一次 Python→Qt 绘制调用 10~22 µs；每格现场造 Qt 对象 8~9 µs。
      结论：**在 Python 宿主里，帧率由"每帧跨界调用次数"决定，而不是由算法决定。**

    ┌──────────────────────────────┬────────────────────────────────┐
    │ 预算                          │ 门槛                            │
    ├──────────────────────────────┼────────────────────────────────┤
    │ 每帧→渲染后端的跨界调用次数      │ ≤ 200 次/帧（当前实现：547 次） │
    │ 每帧新创建的 Qt 对象数          │ ≤ 400 个/帧（当前：约 4400 个）  │
    └──────────────────────────────┴────────────────────────────────┘
    配套写法（都来自实测）：
      · 源数据（贴图坐标、静态几何）**预处理成常量**，每次重建只算一次；
      · 形状裁切改成"外接矩形裁切"，路径裁切只在必要处用（实测每次省 5~10 µs）；
      · 整块只受仿射变换的部件**合并成一次绘制**（数学等价，画质不变）；
      · 每帧的 bound method 先取到局部（`draw = backend.draw`），热路径里不出现 `isinstance/hasattr`。

    ⚠️ 两个"看着更快、其实画错"的坑，写进纪律：
      · 设裁切之前**必须把变换复位成单位矩阵**（否则裁切矩形被上一格的矩阵搬走，画面空白但帧率漂亮）；
      · 任何"合并绘制"类优化，**必须逐像素比对验收**（本项目两次翻车都是这么抓出来的）。

6.2 线程：默认单线程；上线程要有准入条件

    默认：**单线程事件循环 + 脏矩形**。理由（实测）：
      · Python 有 GIL —— 逻辑线程与渲染线程不能真并行（除非后端在 C++ 侧长时间放掉 GIL）；
      · 本项目量到"每帧 752 个顶点过变形链"只花 **0.14 ms**，而 Qt 调用 + 建对象是它的 **200 倍**：
        先压调用次数，收益远大于上线程；
      · 单核跑到 114% 才摸到 145 fps 的地板 —— 线程在那之前不是瓶颈。

    准入条件（同时满足才允许引入渲染线程）：
        ① 单线程 p95 帧时间 > 目标帧时间 × 1.2；② 跨界调用数已达标；③ Metrics 显示 Python 侧
        纯计算占比 > 40%（说明确实是算不过来，而不是被调用开销拖住）。
    上线程之后的通信：先做"双向队列 + 拷贝"（简单、可测），**不直接上无锁 SPSC** ——
    无锁的收益在 Python 侧会被 GIL 与对象开销吃掉，却把调试成本抬一个量级。

6.3 输入区：能力位 + 限频重设
    · 有形状能力 → 用系统形状；只在"看得见的轮廓"真的变了才重设；
    · ⚙ 每次重设都是一趟 X 往返，**不要每帧重设**：改成"当前形状矩形 + 余量（如 30 px）装不下新轮廓时"才重设；
    · 没有形状能力 → 退到窗口级（整窗吃鼠标），并在首次进入时**明确提示一次**（这是"看不见的降级"）。

6.4 闲置策略（桌宠是常驻进程，这条要进 RuntimeConfig）
    ⚙ 实测：闲时把上限从 24 fps 降到 12 fps，CPU 少一半，肉眼无差。
    · 判据不能是"有没有东西在动"，而是"**画面真的变了多少**"：
      ⚠️ 本项目踩过：睡觉时冒的 z 粒子被当成"忙" → 她睡着反而最费 CPU（58%）。
    · 建议 `idle_policy` 做成三段：活跃（满帧）/ 低动（半帧）/ 静止（四分之一帧 + 降低重绘精度）。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
7.1 日志：从第一天起就是「一行一 JSON」

    {"ts":1759100000.123,"lv":"info","tag":"boot","ev":"probe_done","dur_ms":18.4,
     "caps":{"region_input":true,"vsync_source":"x11_present"}}
    {"ts":...,"lv":"info","tag":"frame","ev":"stats","n":300,"p50_ms":16.8,"p95_ms":22.1,
     "cross_calls":196,"new_objs":388,"cpu_pct":58.2,"rss_mb":195}

    ⚙ 为什么是硬要求：本项目的统计一开始是给人看的字符串（`统计：5s 内 120 帧（23.8 fps）｜每帧 2.1 ms…`），
      结果所有量测脚本都在用正则抠数字 —— 换成 JSON 能省掉一整层解析代码和它带来的坑。
    ⚙ 热路径禁止打日志（无论用什么门面）；日志只允许出现在启动、重配、健康检查、每 N 帧一次的统计里。

7.2 健康三问（**这一节是 v1.3 最大的空白**）

    采"性能"指标只能解释"慢"，解释不了"**废了**"。以下三类故障**都不抛异常**，必须主动自检：

    问一｜**输入区还在她身上吗？**
        做法：当前帧 alpha 的包围盒 ∩ 实际设给系统的输入区，形状不一致就报警。
        失败表现：她在那儿，但鼠标穿过去了；或反过来整窗吃鼠标（用户点哪都不响应）。
        ⚙ 本项目踩过：mask 为空但没报错 → 整窗吞鼠标。

    问二｜**画面真的变了吗？**
        做法：present 返回成功后，取固定位置的若干像素（或一帧缩略图）与上一帧比；
              连续 N 帧完全相同 = 失败（"present 成功"从来不等于"屏幕上有东西"）。
        ⚙ 本项目踩过：WebGL2 不可用 → rAF 照跑 48 fps、内存照降，canvas 是空的。

    问三｜**资源在涨吗？**
        做法：句柄/纹理数、进程 RSS，10 秒采一次，做单调性判断（不是绝对值）。
        ⚙ 本项目踩过：长跑 1 小时后内存从 613 涨到 800 MB。

    节奏与动作：每 10 s 一次（和 HealthCheck 同频，共用一次遍历）；
    任一问失败 → 发健康事件 → 按 §8 降级或重建，并记一条 JSON 日志（铁律 3）。

7.3 HealthCheck 与热切换的纪律
    · HealthCheck 是**低频心跳**（发现"事件丢了"），与"能力变化事件驱动"不矛盾；
    · **连续 N 次（建议 2~3 次）失败才升级**为热切换，切换后给冷却期 + 指数退避（防抖动风暴）；
    · 每次切换必须记录：触发源、旧后端、新后端、耗时、是否黑帧。

八、热切换：把承诺分级（别再说"无重启"这种一刀切）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    | 事件                      | 处理          | 承诺                                 |
    |--------------------------|--------------|--------------------------------------|
    | DPI 变化 / 跨屏            | 增量重配      | **画面不黑**；状态不丢                |
    | 用户改配置                 | 增量重配      | 下一帧生效；状态不丢                  |
    | 显示服务切换 / GPU 丢失     | 整链重建      | **状态不丢；画面允许 ≤ 3 帧重建**      |
    | 后端连续失败               | 降级到 raster | 状态不丢；画面允许 ≤ 3 帧             |
    | 屏幕拔掉 / 工作区变化       | 增量重配      | 窗口必须被夹回工作区内（含任务栏）      |

    铁律：**状态机与动画时间轴在切换过程中持续运行**（这是能保证的）；
          ⚙「画面一帧不断」做不到，别写进承诺 —— 承诺做不到的东西，最后会变成"偶发闪烁"的悬案。

    切换时序（沿用 v1.3，补一步）：
        暂停 → drain → 旧 bundle.release() → **自检一次（确认新 surface 可用）** → 新 bundle 注入 → 恢复。

九、生命周期与 Python / Qt 规则
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    · 显式 release() 优先于 __del__；Qt 资源的生命周期以 C++ 侧为准；
    · ⚙ **长生命周期的 Qt 对象必须被 Python 对象强引用持有**：
      QTimer / QWebSocketServer / QShortcut 被 GC 掉时**不报错、静默失效**。
      本项目昨天刚踩：HUD 定时器写成局部变量 → 牌子永远停在「…」；
      更早一次：QWebSocketServer 被回收 → "listen 成功"但端口根本没监听。
      → 这条进 code review checklist。
    · ⚙ 量单函数耗时用 `thread_time()`，**不要用 `process_time()`**：后者是整个进程的 CPU
      （Qt 内部线程的账会一起算进来），本项目因此把 0.5 ms 的函数量成 20 ms。
    · ⚙ 量整机成本要**量整棵进程树**：这类程序常有解码子进程（ffmpeg 等），只盯主进程会漏掉大头。
    · ⚙ 退出阶段不再创建任何 Qt 对象（C++ 侧已析构时创建会崩，这是混合栈最常见的退出崩溃）。

    关闭时序（Shutdown，严格反序，缺一步就会丢帧/崩溃/句柄泄漏）：
        ① 停 FrameScheduler（不再触发新帧）
        ② 等当前 render 跑完
        ③ 停 Worker 线程池并 drain
        ④ IRenderer.release()
        ⑤ IPlatformBackend.release()（窗口/形状/句柄在这里还）
        ⑥ 关闭 ILogger / Metrics（最后关，前面每一步都要能记日志）
    ⚙ 验收：连开连关 20 次，进程退出码稳定、无残留句柄（`lsof`/句柄计数回到基线）。
